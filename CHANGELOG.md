# Changelog

Changes of this fork (sandyhq/zend), newest first. Upstream changes are in the git history.

## 2026-11-25

### Added
- Development mode with no edge: \`edge-url\` = \`none\` (file or \`ZEND_EDGE_URL\`) keeps the \`edge-token\` identity (org, user, data folder) but opens no edge transport, no "Reconnecting…" pill; for an install whose edge is gone, one step: \`echo none > ~/.config/zend/edge-url\` (\`crates/engine/src/lib.rs\`, \`crates/cli/src/env.rs\`, \`apps/zgx/src/engine/manager.rs\`, \`docs/reference/build-and-deploy.md\`).
- Workers, subscription login per worker (step 4d-4 for workers): `zend worker login allow|rm|list <worker> <provider>` lets a worker's Pi turns run on the server's pi login; before each turn the server writes that provider's access-only entry into the worker's read-only `conf/login/`, the worker copies it into its pi's `auth.json` (444); a key wins; rm, `zend worker stop` (new), `rm` and engine start remove it (`crates/engine/src/worker_logins.rs`, `crates/engine/src/worker.rs`, `crates/engine/src/peer_view.rs`).
- Workers, subscription login fixes from review: lent per turn (one provider's at a time, gone once the turn settles), a per-worker lock across check, refresh and write, `login rm` ends the worker's live turns on it, the worker's copy on a tmpfs (`/run/zend-login`, workers made before need to be made again), names checked on every login method.
- Worker sessions, review fixes: a worker's device id is its server's (`worker-<12 hex of its key>`), never what it says; its rows can't take any id this device knows (archived chats and paired servers' ids too), carry a fixed set of chat fields, sessions only of chats shown; a createChat to it carries only chatId, spaceId, config; a worker made with the old `work` project gets its own at its next start (`crates/engine/src/peer_view.rs`, `crates/engine/src/workers.rs`).
- Worker sessions from the server: each running worker shows in its server's window as a device with its `work` project, and a chat made there runs in its `/work` over the worker's socket (harnesses, models, createChat/setChatConfig, QueueCommand, WatchDocMessages only); a worker's rows are hostile input (its device id checked, chats only in its project, no folders, this device's ids win) and shown to this device's own callers alone; `zend worker run <name> "<prompt>"` prints the reply (`crates/engine/src/peer_view.rs`, `crates/engine/src/workers.rs`, `apps/zend/src/worker_cli.rs`).
- Paired servers, lent login review fixes (step 4d-4): the lent `auth.json` is kept in `peer-login-tokens/` in Zend's data (700) and mounted read-only into the sandbox (`Sandbox::with_agent_file`), so a link the sandbox puts in its state folder can no longer have Zend delete or overwrite the owner's pi login; Zend acts by no path in the state folder. The file goes with its run, on chat delete and at engine start. A server hears only "no credential for <provider> on this device". A failed refresh waits 60 s.
- Paired servers, subscription login per server (step 4d-4): `zend peer login allow|rm|list <server> <provider>` (anthropic, openai-codex) lets a server's sandboxed Pi chats run on this device's pi login. Each turn gets an `auth.json` of its own (that provider's access token, `refresh` empty) in its `PI_CODING_AGENT_DIR`. The host's pi refreshes a token with less than 10 minutes left first (`pi auth print-bearer-token`). A key wins over a login. `rm` and unpair take the file out and end live runs (`crates/engine/src/peer_logins.rs`, `crates/harness/src/sandbox.rs` `with_agent_dir`).

### Fixed
- Sandbox, a Node agent's binds kept to its install: a package the agent's script loads is bound only when it lies in its install (pnpm's global install and store, npm's `lib/node_modules`), else the run is refused; a script outside any package (or in `~/bin`, `~/.local/bin`, the home) is bound as its file alone; nothing in a hidden folder of the home is bound unless it lies in a tool folder, and Pi's folder (`~/.pi/agent`, `PI_CODING_AGENT_DIR`) never, but for its `install/`; a relative `PNPM_HOME` is not looked in (`crates/harness/src/node_entry.rs`, `crates/harness/src/sandbox.rs`, `crates/harness/src/executable.rs`).
- Sandbox, agents installed by pnpm or npm: a sandboxed Pi installed by pnpm (or npm) died with MODULE_NOT_FOUND, since the sandbox bound only its launcher's folder. A Node launcher (pnpm's shim, npm's link to a `#!/usr/bin/env node` script) now runs as node on the script, with node's real file and the script's package and dependencies bound read-only at their real paths and pnpm's dependency links recreated; nothing else of pnpm's store. A pnpm shim is read, not run: one in any other form is refused with the reason. Pi's discovery (running and the host refresh of peer and worker logins) also looks in `$PNPM_HOME`, `$PNPM_HOME/bin`, `$XDG_DATA_HOME/pnpm` and the `bin/` of pnpm's default homes (`crates/harness/src/node_entry.rs`, `crates/harness/src/sandbox.rs`, `crates/harness/src/executable.rs`).
- Paired servers, live-test fixes: a run a server's chat won't take (no key kept for that server and provider, a harness that can't run sandboxed) is refused to the sender at once with the reason, logged, and shown under the prompt in the window; a run refused as it starts leaves an error turn in the chat instead of only the user's message. A server that unpaired this side (its handshake's 401) drops out of the window at once; one not reached shows offline from the first failed redial and its rows go after 10 minutes.

- Phone link security: the phone and the computer prove the link's key to each other with a challenge (HMAC-SHA256 over fresh nonces, `crates/rpc/src/link_proof.rs`), the computer first, so the key never crosses the wire and an address that answers without it (a wrong DNS answer, a stranger) learns nothing; the phone also dials only tailnet addresses. - Phone link security: a phone's methods are a list of their own, no longer the agent token's plus a window's: agent accounts, plugin installs and tools, templates and themes made or switched, visuals published and device stats are refused (`crates/rpc/src/remote.rs`). - Phone link security: the link admits only a peer Tailscale itself names as a node of the tailnet (`tailscale whois`), not any address in 100.64.0.0/10 (a carrier's CGNAT shares it), and it finds this device's tailnet address only through `tailscale status --json`, no longer from an interface in those ranges: without Tailscale's word it stays off (fails closed).
- Phone link: in IP mode the code holds an address the link listens on, never a tailnet address it couldn't bind.
- Logs: the WebSocket crates (tungstenite, tokio-tungstenite) are capped at debug whatever `RUST_LOG` or `ZEND_LOG` says: at trace they logged the upgrade request (the IPC bearer token) and every frame (a phone-link status holds the link's key).
- Phone link: a phone re-paired while it is a window onto a desktop hangs up on that desktop's engine instead of asking it to stop (the desktop refuses StopEngine from a phone, so every re-pairing failed with "the engine didn't stop"), and the relay and desktop it kept are one transaction: a failed re-pairing puts both back (`apps/zgx/src/phone_link.rs`, `Rpc::hang_up`).

A Stop now names the sends it stops (`Interrupt.cancels`, ADR 0007) and the host decides by that, not by clocks or ledger order: across devices and by relay a send named by a Stop never runs after it, and a late Stop never stops a turn its sender didn't know of. What a Stop names stays cancelled when the Stop itself is moot or gives way to a newer one, and across a restart of the host; a Stop waits for no send (a named one checks the names as its last step before the agent, a revival after a restart too) and kills only a runtime handed nothing its sender never saw, decided and retired in one step (`runtime_survival::a_named_send_stalled_before_its_runtime_never_starts`, `a_stuck_queue_send_does_not_hold_up_the_stop_naming_it`, `run_recovery::a_turn_a_stop_named_is_not_revived_after_shutdown`); one aimed at a turn a rewind removed is moot. A Stop from an older engine keeps the old rule. A send its sender had seen (its row up to the Stop's turn) is claimed like a named one, every road to the agent asks one check that reads disk and memory (a queue row sent now after a restart too), and a runtime remembers every message it was handed, with no count (`runtime_survival::a_queue_row_a_stop_named_is_not_steered_in_after_a_restart`, `a_send_the_stops_sender_saw_stalled_before_its_runtime_never_starts`, `a_stop_leaves_a_runtime_handed_an_unseen_message_before_256_named_ones`). A send a Stop claims while its run is preparing never reaches the harness, and the Stop doesn't wait for the preparation; the turn a Stop was aimed at is claimed even before its row reaches the host (`a_send_a_stop_claims_while_it_prepares_never_reaches_the_harness`, `a_queue_row_a_stop_was_aimed_at_is_not_steered_in_after_a_restart`). A Stop carries its sender's doc version (`based_on.frontier`), and what its sender saw is the rows that version holds, not the rows before its turn in the host's order: a turn started after the Stop was built is never killed or claimed by it, wherever the merge puts it; the version is read back from the doc, or from the ledger for a relayed Stop, after a restart; the per-send check is a lookup instead of a transcript walk (`a_stop_spares_a_turn_its_sender_never_saw_merged_before_its_aim`, `a_stops_version_is_read_back_from_the_doc_after_a_restart`). Whether that version held a row is read from the doc's ops (the one that gave the row its id, the ones that removed it), not from the row's map: a send the Stop saw stays stopped after its row is rewound and the host restarts, and when its row's id reaches the host after the Stop; a send whose empty row the sender held before it had an id runs (`a_send_a_stop_saw_stays_claimed_once_its_row_is_rewound_and_the_host_restarts`, `a_send_a_stop_saw_is_claimed_when_its_rows_id_arrives_after_the_stop`, `a_stop_built_before_a_row_had_its_id_lets_that_send_run`, `zend-doc stop_version`). The window's Stop says the version of the transcript it shows, not of the doc, which may hold an import not shown yet (`zend-client a_stop_says_the_version_of_the_transcript_it_was_pressed_on`), and an engine Stop whose caller named its sends carries its version too (`an_engine_stop_with_its_sends_named_says_its_version`).
