# Features of this fork

What sandyhq/zend adds on top of the upstream app, one paragraph each, with where to read how to use it. Upstream's own features are in [README.md](../README.md) and the other files in this folder. What comes next: [roadmap.md](roadmap.md). What changed when: [CHANGELOG.md](../CHANGELOG.md).

## For people reading a chat

### Every tool's row opens to what it did
A tool's row in a reply's work opens (a chevron at its end shows under the pointer) to what that call did, drawn for its kind: a read of a picture shows the picture the read gave the agent (the reply's frame, lightbox and copy; kept by the device that ran it, up to 10 MB, from pi and Claude Code; an older read shows its path and says no picture was kept); a read of text, its lines coloured by language; an edit, write or patch, its diff; codemode, its script as JavaScript, then its result; an MCP or other tool, its arguments key by key (JSON for nested ones) and its result (JSON as JSON); a web search, its answer as prose. Commands open as before. What it shows isn't in the chat's doc: the window asks the device that ran the tool, which reads its run journal (`ReadToolExchange`, `ReadToolImageChunk`), with secret inputs, secret files' contents and secret commands' output kept on that device. That last is by name: a codemode script that reads `.env` (`tools.read` inside it) is one call to Zend, so its result gets only the text redaction every output gets (private key blocks dropped, `KEY=value` values and token shapes hidden), not withheld whole. A device that is offline or runs an older Zend says so, and a press asks again. Pi's edits now carry their diff (from the tool's own numbered diff), Codex's a one-file change's patch (the app-server's `FileUpdateChange.diff`). In the zgx window.

## For agents working with other agents

### Child sessions and child events
A chat can start other chats as subagents, side chats or child sessions (`create_chat`, `create_chats`). The parent does not wait or poll: when a child settles a turn, the engine sends the parent a `[Zend event: …]` message with the outcome and the child's last reply or question.
How to use: [mcp.md](mcp.md), sections "Parent links", "Child events" and "Delegating across providers".

### Visuals that ask (`ui.answer`, `update_visual`, `read_visual`)
An agent's visual can ask: text fields, checkboxes, choices and a button that puts the reader's entries as words under the draft in the composer, never sent by itself. Zend keeps the entries by input name. While a visual waits for its answers and its place has scrolled out of view, it is pinned above the composer (scrolled back to its place, it returns there, keeping the field being typed in); once the person sends a message holding its heading line (`### <title>`, whatever else they rewrote) it shows "Answers sent". The pinned visual can be folded to its title line with its minimise button, or closed by hand with its × ("Closed without answers": nothing sent, and the agent is told so once, on the person's next message). The agent changes it in place with `update_visual` and reads it with `read_visual`; entries are read-only to it until sent, and each child event names the parent's open visuals so a lead keeps the visual up to date instead of asking again.
How to use: [visuals.md](visuals.md), section "Asking the reader"; [mcp.md](mcp.md), "Child events".

### Visual kit (`ui.kit`)
Ready-made components for visuals, each one call with data instead of a hundred lines of nodes: `ui.kit.Form` with `Input`, `TextArea`, `Checklist`, `Choice`, `Radio`, `Select`, `Toggle`, `OptionCards`, `FollowUps` asks the reader and ends in the answer button; `Slider`, `Stepper`, `Rating`, `ListEditor`, `EditableTable` and `Quiz` ask for numbers, lists, rows and quiz picks; `Timer` counts down; `Card`, `Callout`, `KeyValue`, `List`, `Steps`, `Status`, `Progress`, `Metric` and a few more show things. Built from the existing nodes in Zend's style; every renderer has them. How to use: [visuals.md](visuals.md), section "Kit"; examples in `visuals/`.

### Code in visuals (`ui.code`, `ui.null`)
A visual can show source lines in their language: `ui.code` colours them with the window's own highlighter (the one Markdown code blocks and diffs use), with line numbers or its own gutter and lines marked added, removed or to look at. The kit's Code, Snippet, File and Diff use it, so a diff keeps its added and removed washes and colours each file by its language. `ui.kit.Json` shows `ui.null` as null and reads a JSON text (`text = "<json>"`), naming the line and column of a mistake. In the zgx window; the other renderers show the lines plain. How to use: [visuals.md](visuals.md), "Nodes" and "Kit"; examples in `visuals/code/`.

### Pictures in visuals (`ui.image`)
A visual can show a picture the agent passes in `assets` (PNG, JPEG or WebP), at the reply's width or a height of its choosing: a screenshot with numbered regions named on hover and picked by a click, two pictures over each other with a line the reader drags between them, or a grid. The kit's Image, Gallery, Compare and Hotspots use it. A name that isn't in `assets`, or a file that isn't a picture, is an error `show_visual` names. Nothing is fetched from the network: the file travels with the visual, so the picture shows on other devices and in plugin pages too. In the zgx window; the other renderers show a line naming it. How to use: [visuals.md](visuals.md), "Nodes" and "Kit"; examples in `visuals/media/`.

### Instructions from plugins (`session.instructions`)
A plugin can give text to the agents of your chats: for every chat on the device, one project's chats, or one chat. The text goes whole into the agent's system prompt as its own section and is renewed every turn. 8 KB per chat. Settings shows each plugin's text, read only. Works for chats on Pi; other harnesses run without it.
How to use: [plugins.md](../apps/zgx/docs/plugins.md), section "Telling your agents". Example: `apps/zgx/plugins-dev/delegation`.

## For people in a chat

### A phone-sized window (compact)
Below 600 pt wide (a phone, a narrow split) the window rearranges instead of squeezing: the sidebar is a drawer over the page (the title bar's toggle or a swipe in from the left edge opens it; a tap beside it, a swipe back, Escape or choosing anything closes it), the panel opens as a sheet over the whole page, Settings shows its list of pages or one page with a Settings button back to the list, and the title bar's controls are 44 pt touch targets (no Forward). Wider windows look exactly as before.
Code: `apps/zgx/ui/screens/shell/fit_policy.luau` (`COMPACT_BELOW`), `fit.luau`, `init.luau` (the drawer), `settings.luau`, `ds/title_bar.luau` (touch). Plan: `plans/android-zgx-app` (G4).

### Typing, selecting and dragging on the phone
The Android app types, selects and drags like other Android apps: the keyboard's composing text, suggestions, voice typing, umlauts and emoji reach the composer, Enter is a new line (send with the button), a long press on text shows Android's selection handles and floating toolbar, and a sidebar row or tab drags only after a long-press hold (a swipe scrolls).
Code: `apps/zgx/android/java/` (ZendActivity, SelectionUi), zgx-desktop `android_ime.rs`, `touch.rs`. Tests: `apps/zgx/android/e2e/run.sh`.

### Connect a phone by QR code
Settings → Devices on a computer has Show code: a QR code with this computer's relay (edge) address and its own key, for a minute or until a new device joins. On the Android app the same page has Scan code (the camera; Android asks for it the first time) and a box to paste the code's text. The phone keeps the relay and key in its own files and reconnects at once; your computer's sessions then show on it. Anyone who sees the code can join your relay as you: show it only to your own phone.
Code: `apps/zgx/src/phone_link.rs`, `src/android_camera.rs`, `ui/screens/settings/devices.luau`. Plan: `plans/android-zgx-app` (G3).

### A phone link over the tailnet
With no relay, the phone can be a window onto this computer directly: Show code (Settings → Devices) turns on the phone link, a second listener of this computer's engine on its tailnet address only, and the code holds that address (its MagicDNS name or its tailnet IP, chosen under it), the port and the link's own key. A phone that scans it keeps the computer, runs no engine of its own and shows exactly this computer's sessions: reading, sending and new chats all go to its engine, and it reconnects when the engine restarts or the network comes back. The computer must be running Zend. The link refuses addresses and peers outside the tailnet, takes only its own key (proved both ways by a challenge, the computer first, so the key itself never crosses the network), and serves only what a window needs (no credentials, sign-in, vault, relay commands or plugin authority). The switch beside it turns it off again; New key cuts every phone that had the old one. It stays on across restarts until turned off. While the phone scans, the camera's picture shows in the scan area. A phone linked this way uses the computer's account as it is: the username is claimed on the computer (setup on the phone passes over the account's steps, and Profile says so).
Code: `crates/rpc/src/remote.rs`, `crates/engine/src/phone_link.rs`, `apps/zgx/src/phone_link.rs`, `apps/zgx/src/engine/rpc.rs`, `ui/screens/settings/devices.luau`. Plan: `plans/android-zgx-app/direct-link.md`.

### Paired servers (peer link)
Two of your Zend servers can be paired over the tailnet with no relay between them: `zend peer pair` on one prints a one-time code (its key, tailnet address, port and a secret, good for 10 minutes), `zend peer join <code>` on the other pairs them, and both keep each other's public key in `peers.json`. Each engine has its own Ed25519 node key (`node-key`, mode 600). A paired server dials in on a listener of its own (the IPC port + 1, tailnet addresses only, nodes Tailscale names only); both sides prove their key with a signature over fresh nonces, the called side first. Each side decides alone what the other may do there: nothing at first, then grants set with `zend peer grant <peer> <grant>…`: `sessions.read` (watch chats and read their messages), `sessions.run:<project>` (create chats in that project and run and read its own, confined to the project's folder), `sessions.run.unconfined:<project>` (any chat of that project, unconfined: full trust, since such an agent runs as you on this server and can read Zend's IPC token and anything else of yours), `projects.share:<project>` (list and read that project's files by a path from its root: opened beneath the project's folder with no symlink followed (openat2 `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS` on Linux, a no-follow walk elsewhere, refused on Windows), regular files with one link only; never a folder that holds Zend's data or the home folder, or one in a dot-folder of home; never a file under Zend's data; and never `.env`, `.env.*`, `.netrc`, `.npmrc`, `.pypirc`, `*.pem`, `*.key`, `id_*` or `.git/config`), `workers.manage`, and the area grants of step 6 (below). `sessions.read` shows only this device's own chats and sessions, a chat's folder relative to its project. Of a chat it may run (its own under `sessions.run`, any chat of a project it holds `sessions.run.unconfined` for, checked against its grants as they are now) a server may also set the config (`Mutate` `setChatConfig`: a confined chat keeps this side's sandbox, access and plan mode, and model options its model doesn't list are refused, as for `createChat`), rename it, mark it seen, archive it and delete it (only when every chat that would go with it is one it may reach too); of any other chat, none of these, and no other `Mutate` op without an area grant (step 6). An agent in a chat a server started calls as that server, with its grants now; its children are that server's too. A confined chat takes this side's sandbox, access (supervised) and plan mode, not the server's, and model options its model doesn't list are refused; whether a chat a server made may run is checked at every turn against that server's grants as they are now (`sessions.run.unconfined` for an unsandboxed chat, either grant for a sandboxed one): a chat started unconfined doesn't run once the grant is only `sessions.run`, and a lost grant or unpairing ends the live runs of the server's chats there and then, and no steer, child's event, queued message or revival after a restart starts one; a copy (fork) of such a chat stays that server's, sandboxed to the same folder; one created with no config gets this device's default harness under the same pins. A sandboxed Pi run inlines an attached image only from a file opened beneath its project (`openat2` `RESOLVE_BENEATH`), one link only. Pairing pins the other side's Tailscale node (its stable ID, from `tailscale whois`); a key arriving from another node, or dialled at an address now another node's, is refused. Pairing, grants and unpairing are this device's own: never over a peer link, the relay, a phone or from an agent. `zend peer unpair` forgets a server and ends its connections. A chat a server creates under `sessions.run` is sandboxed on this host to the project's registered folder (`sandbox_chat`, before it exists): its agent runs under bubblewrap in that folder, or not at all; a chat its agent starts stays in that project, sandboxed to the same folder. In that folder the agent can't change what your own tools run or load from it later: `.git` (and a worktree's git folder inside the project), `.pi`, `.claude`, `.codex`, `.opencode`, `.cursor`, `.vscode`, `.idea`, `.envrc`, `.githooks` and `.husky` are mounted read-only where they exist (in the project's folder and each folder down to the chat's), and none is made where it doesn't. Everything else there it can write, `AGENTS.md`, build scripts and code included: from the first such run, treat the folder as untrusted for your own unconfined tools (review its changes before you build or run them).
**Own working copy (step 4d-2).** A chat a server creates under `sessions.run:<project>` doesn't work in your project folder: it gets a copy of its own in Zend's data (`peer-copies/<chat>`): a detached git worktree at your HEAD when the project is a git repository (no branch of it in your repository; every git call in your repository runs with none of your hooks and no fsmonitor), else a copy of its files (no `.git`, no file that holds secrets by its name: `.env*`, `.netrc`, `.npmrc`, `.pypirc`, `*.pem`, `*.key`, `id_*`, and not Zend's data). The sandbox's root and the chat's folder are that copy; your folder is not mounted. Its agent's children work in the same copy; any other chat confined to it is refused. Engine git keeps skipping the copy and runs again in your own folder. What it changed comes back as a patch, taken against a snapshot repository of the copy's own (`peer-copies.meta/<chat>/git`, run with a cleared environment, no config, hooks or attributes: nothing the agent wrote is run by it). A snapshot is taken only while nothing of the copy runs: no live run of a chat in it, and no process on this host in a mount namespace that has the copy mounted (a sandbox's: the kernel keeps it while any process of the sandbox lives); runs of its chats wait meanwhile. Before it the copy's files (those git would read, not what its `.gitignore` leaves out) are measured with lstat: at most 50,000 files, 20 MiB a file, 500 MiB in all (apparent sizes), else refused naming the files. `zend peer changes list` (each chat's changed files and the tree they make), `show <chat>` (the diff on stdout; its files, the tree and the exact apply command on stderr), `apply <chat> <tree> [--allow <path>]…` (writes exactly the tree you were shown, all or nothing; refused when the copy changed since, a chat in it runs, a file changed in your folder since the copy, a path is a symlink or goes through one, leaves the project, is in `.git` or one of the read-only names above at any depth, or is a file your tools run on their own: `.gitattributes`, `.gitmodules`, `.lfsconfig`, `.pre-commit-config.yaml`, lefthook files, `flake.nix`, `flake.lock`, `shell.nix`, `.mcp.json`, `opencode.json`, `.zed/`, `.devcontainer/`, `.github/workflows/`; files that instruct your agents, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules`, `.windsurfrules`, only with `--allow` for each path; a change of mode only is applied) and `discard <chat>` (removes the copy; the chat runs no more). Applying is a review step, not a filter: code and build scripts are applied as you read them. The CLI prints names and patches with control and bidirectional characters escaped. These are this device's own: never over a peer link, the relay, a phone or from an agent.
**API keys per server (step 4d-3).** A confined chat of a server runs on an API key you keep for that server, never on your own logins: no login file of yours is mounted for it, and its environment has only that key, under its provider's variable (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, …, from Pi's provider list). `zend peer key set <server> <provider>` reads the key from stdin, `zend peer key rm <server> <provider>` takes it away, `zend peer key list` names servers and providers only. Keys are kept in `peer-keys.json` (mode 600) in Zend's data, never synced and never returned over any connection. A run whose model has no known provider, or whose provider has no key for that server, is refused: the server is told only "no credential for <provider> on this device"; why, and the command to set one, go to this device's log. `rm` and unpairing end the server's live runs and start no new one. `sessions.run.unconfined` keeps running in your folder on your logins, as before. A login can be lent instead of a key (step 4d-4, below).
**Agents installed by pnpm or npm, sandboxed.** An agent CLI a Node package manager installed is a launcher in a bin folder that loads files elsewhere: pnpm's shim runs its own node on a script in `global/`, both links into pnpm's store; npm links to the package's `#!/usr/bin/env node` script. In a sandbox Zend runs node on that script, and binds read-only only node's real file and the script's package and the packages it depends on (as `node_modules` resolves them, at their real paths), with pnpm's dependency links recreated as links: never the whole store, `global/` or the home. Every package must lie in its install (pnpm's global install and store; npm's `lib/node_modules`): a dependency linked anywhere else (`~/.pi/agent`, another project) refuses the run with the reason in the log. A script in no package, or in `~/bin`, `~/.local/bin` or the home itself, is bound as that file alone. Nothing below the home in a hidden folder is bound unless it lies in one of the sandbox's tool folders, and Pi's folder (`~/.pi/agent`, `PI_CODING_AGENT_DIR`) never, but for its `install/`. A pnpm shim is read, not run: only the form pnpm writes is taken (its `cmd-shim-target` and `exec` lines naming node and that one script); one with another target, node options, `NODE_PATH`/`NODE_OPTIONS` or anything else is refused with the reason in the log. Pi is found in pnpm's global bin without it on the PATH: `$PNPM_HOME` (when absolute), `$PNPM_HOME/bin`, `$XDG_DATA_HOME/pnpm` (and `/bin`), `~/.local/share/pnpm` (and `/bin`), `~/Library/pnpm` (and `/bin`), for runs and for the host refresh of a lent login alike.

**Your subscription login per server (step 4d-4).** With no API key, a server's confined chat can run on this device's own pi login (a browser-login subscription) for one provider, if you allow it: `zend peer login allow <server> <provider>` (`anthropic` or `openai-codex`), `zend peer login rm <server> <provider>`, `zend peer login list` (names and providers only; `peer-logins.json`, mode 600, in Zend's data, never synced or answered over a connection). Each run of such a chat gets a login file of its own, kept where no sandbox reaches (`peer-login-tokens/<chat>.<run>.json` in Zend's data, folder 700, file 600) and mounted read-only by bubblewrap as `auth.json` in `pi-agent/` in the chat's state folder, which is its `PI_CODING_AGENT_DIR`: the agent can read it but not change, replace or remove it, and Zend never writes, checks or removes anything by a path in the state folder (the sandbox may have put a link there; bubblewrap refuses to mount through one). The file holds only that provider's access token and expiry (and Codex's account id), with `refresh` empty and no other provider. It is read from the host's pi `auth.json` (`PI_CODING_AGENT_DIR` or `~/.pi/agent`), which is never written by Zend and never mounted. A host token with less than 10 minutes left is first refreshed by the host's own pi, outside the sandbox (`pi auth print-bearer-token --provider <p> --min-expiry 10m`: pi's own refresh under its file lock, its output dropped). If that fails, or there is no pi or no login, the run is refused (the server hears only "no credential for <provider> on this device"; the reason goes to this device's log), and a failed refresh isn't tried again for 60 s. A key kept for the server and provider wins over the login (that turn gets no login file). The file goes when its run ends; `rm` and unpairing remove it at once and end the server's live runs on it, and the next run is refused; deleting the chat removes it too, and the engine clears the folder when it starts. The token is in no log line, journal, error or reply. The agent can read the access token while it runs, and a token it copied stays valid until it expires (a few hours); the refresh token never leaves the host. Only Pi uses it. Workers get the same, below ("Your subscription login per worker").
**In the window (step 4e).** A server this device joined shows in its own window as a device, with no relay or edge: the engine dials it over the peer link and merges what that server's grants let it see into the window's lists (`WatchDevices`, `WatchChats`, `WatchSessions`, `WatchSpaces`): its device (online while the link is up; offline from the first failed redial, its rows kept 10 minutes, then dropped until it's reached again; all of it gone at once when that server unpaired this side or grants it nothing, its handshake's 401 counting as a refusal), its chats and sessions under `sessions.read` (none without), and the projects its grants name (by name, never their folder) even before they hold a chat. A call that names the server's device, one of its chats or one of its projects goes to it over the peer link and is answered there, under the grants it gave this side: opening a chat reads its transcript there, a new chat made in one of its projects (Mutate `createChat`, made at the project's folder there, with the model picked in the composer) is made and run there, and a refusal (no `sessions.run` for that project) shows in the composer in the server's words. Only this device's own window and CLI see the merged lists; a server dialling this device still sees only this device's own rows (the peer gate), so pairing exposes nothing more of it; a linked phone sees none of a server's rows and can't reach it. What a server says is display only: an id this device holds (a chat, a project, its device) is always answered here and never sent to a server; a server's row with an id this device or another server has, or a chat in such a project, doesn't show (logged once); a server claiming this device's id, a Cloud id (`cloud-…`) or a device another server already has (the first paired keeps it) shows nowhere. Its rows carry its own device id, no folder but one relative to its project, no harness folder, checkout or source; its device shows the capability `paired-server` only. A message over 4 MiB from it ends that connection (redialled), and a list over 5,000 rows is dropped; this side's peer listener likewise takes no message over 4 MiB from a server dialling in. Every call some grant can open is sent to it (step 6b, below), the ops of its chats with no `targetDeviceId`; the same ops of this device's own chats stay here, and every config is sent (none answered here as unchanged). A call aimed at a server (`targetDeviceId`) that names this device's own chat, project or device is refused here, saying so, and never sent. New project doesn't browse a paired server's folders: its device says that isn't available there (add the project on that server, and a project it grants shows). A server that grants this side nothing is logged once (INFO), on each side, until that changes, not at every redial. A call no grant ever opens (`never`, step 6) is refused here and never sent; one the server didn't grant is refused there and comes back in its words. A run sent there carries the words and the agent picked, none of this device's folder, attachment paths, worktree, MCP servers or resume. A run a server's chat won't take (no API key kept for that server and the model's provider, an agent that can't run sandboxed: only Pi does) is refused to the sender at once in those words and logged there, and the window shows them under the prompt; a run refused as it starts (any chat) leaves an error turn under the user's message with its reason. A server's `EngineInfo` reply now also names what it granted the caller (`peer: {reads, projects: [{id, name, run, share}]}`). Not yet: reviewing a server chat's patch (`zend peer changes`) in the window.

**Grants by area (step 6).** Every call a paired server can make has one scope, in one table (`crates/rpc/src/peer_scope.rs`, `peer_scope(method, op)`, of `Mutate` by its op, no fallback: a test fails when a method or a `Mutate` op has no row). Besides the session grants above, `zend peer grant` takes: `projects.manage` (projects, repositories, branches, worktrees, browsing folders and drives, project actions; `Mutate` `createSpace`, `renameSpace`, `setSpaceIcon`, `deleteSpace`), `files` (any file by any path, read and write, search, diffs, change requests), `settings` (title and commit settings, sidebar, plugins, templates, themes, device stats; `renameDevice`, `changeSidebarPin`), `logins` (harness installs, agent accounts and logins, ACP agents and their keys), `updates` (Zend's and the harnesses' updates), `terminal` (terminals, project actions, background tasks), and `full`: all of these, `sessions.read`, `workers.manage`, and the rest (queue, visuals, uploads, attachments, voice, fork and rewind, the other chat ops). `full` doesn't run or share a project: those stay `sessions.run[.unconfined]:<p>` and `projects.share:<p>`. `terminal`, `files` and `full` are full access to this machine, as you: `zend peer grant` says so. Never open to a server, with any grant: pairing, grants, peer keys and logins, the account (sign-in, sign-out, tokens, step-up, deleting it), orgs, Cloud, billing, vault, GitHub connect, the phone link, stopping Zend, removing a device, and the window's own channels (81 methods and `removeDevice`). Each call is checked twice, by the peer listener and by the engine (`peer_gate`), and names only this device's own: a `chatId`, `spaceId` or a `Mutate`'s device must be this device's. Calls under `files`, `terminal`, `logins` and `full` are logged at INFO (method and the server's key prefix, no content). An agent in a server's chat keeps the session grants only, whatever the server holds. In the window (6b) every call that names a server and isn't `never` goes to it, streams and chunk calls with it; a call naming this device's own chat, project or device is refused first and never sent; a call the server didn't grant comes back refused in its words (`peer_refused`). Such a call still travels: a key typed into a server's login settings reaches that server even when it then refuses it.

Code: `crates/rpc/src/peer_link.rs`, `crates/engine/src/peer_link.rs`, `crates/engine/src/peer_view.rs`, `crates/engine/src/rpc/peer_gate.rs`, `crates/engine/src/peer_chats.rs`, `crates/engine/src/peer_copies.rs`, `crates/engine/src/peer_keys.rs`, `apps/zend/src/peer_cli.rs`. Plan: `zend-home-repo/plans/client-server` (steps 4a–4e).

### Workers (step 5)
A server can run agents in workers: rootless Podman containers it makes for itself, each running Zend's engine in the worker role with one project, `work`, at `/work` (a named volume; its id `work-<first 12 of the worker's key>`, set by the server). `zend worker create <name> [--image <image>] [--key <provider>] [--memory 4g] [--cpus 2] [--pids 512]` makes one and starts it; `list`, `start <name>` and `rm <name> [--keep-volumes]` manage them (this device's own: never over a peer link, the relay, a phone or from an agent). A create that fails takes away what it made (key secrets, container, folders, the volumes it made). The image is `localhost/zend-worker:latest`, built by `infra/worker/build.sh` from a built `zend-engine` and the engine image already on the server (no download, `--pull=never`; the base image's git identity, `/etc/gitconfig`, is left out). A worker belongs to its server alone: the server makes the worker's Ed25519 key, gives it its own public key and pins the worker's (`workers.json`); the worker's book holds only that server, granted `sessions.read` and `sessions.run.unconfined:<its project>`, so it serves engine info, harnesses and models, its chats and sessions, chats created in its project, runs and messages of its server's own chats there, and refuses everything else and every other key at the handshake. It opens no connection itself (no tailnet or phone listener, no edge, no release checks): the server dials it over a unix socket in a 0700 folder of its own data (`workers/<name>/run/worker.sock`, bound into the container), so no port on loopback or the tailnet is open to other users. A worker is as trusted as its agent, so everything from it is hostile input: the server dials the socket only as itself (opened `O_PATH | O_NOFOLLOW`, a socket or refused, no symlink followed), takes no message over 16 MiB from it, and shows of what it says only what the window's rules below let through. Network: pasta, IPv4 only, no address mapped to the host and no forwarded ports, DNS sent to a public resolver (1.1.1.1), not the host's (no tailnet names); on every start, before the container's first process runs, the server takes the blocked networks afresh (the sandbox's: private ranges, the tailnet's 100.64/10, link-local and cloud metadata; and the host's own addresses and subnets, docker's and Podman's bridges with them) and adds an unreachable route for each in its network namespace. A running worker keeps the routes it started with: an address the host gains later is blocked from its next start. The container has no capabilities (`--cap-drop all`, `no-new-privileges`), so nothing inside changes a route, and its engine checks the routes are there before it serves (else it doesn't start). The internet stays reachable for model APIs. It has a user namespace of its own (`--userns=auto`, its root not the server's user), runs as uid 1000 there, and is capped at 4 GiB memory with no swap, 2 CPUs and 512 processes by default. `--key <provider>` reads an API key from stdin into a Podman secret, given to the container as the provider's variable (`ANTHROPIC_API_KEY`, …); no login file of the owner's goes in. No bubblewrap inside: the container is the sandbox. Not yet: `workers.manage` over the peer link, a cap on /work's size. Code: `crates/engine/src/workers.rs`, `crates/engine/src/worker.rs`, `crates/rpc/src/peer_link.rs` (`serve_peer_unix`, `connect_peer_unix`), `apps/zend/src/worker_cli.rs`, `infra/worker/`.

**Worker sessions from the server.** Each running worker shows in its server's own window as a device named as the worker (capabilities `paired-server` and `worker`), with one project, `work`, and its chats and sessions, merged by the same machinery as a paired server's (`crates/engine/src/peer_view.rs`, a worker source beside the paired servers: dialled over its socket, redialled after a loss, a newly made or started worker at once). A chat made there (by its device or its project) is made in the worker's project whatever folder or project the window names, and runs in `/work`; its transcript reads back through the window. Only harnesses, models, `Mutate` `createChat`/`setChatConfig`, `QueueCommand` and `WatchDocMessages` are sent to a worker (no engine info, files, keys or other ops: refused here, never sent), a run with the words and agent only. What a worker says is hostile input. Its device id is its server's word, `worker-<first 12 hex of its key>` (from `workers.json`, shown by `zend worker list`), stamped on every row of it; what its engine says it is only proves it answers (and if that names this device, a paired server or a Cloud id, or isn't a plain id, the worker shows nowhere). No paired server shows with a `worker-` id. Its rows can't take an id this device knows: this device's own and its chats (archived ones too), projects and devices, and any paired server's ids (paired servers merge and are called first). Of its chats only those in its project show, each with a fixed set of fields (`id`, `title`, `archived`, `spaceId`, `config`, `lastMessageAt`, `lastMessagePreview`, `createdAt`, `lastSeenAt`, `parentChatId` only when it names another of its chats, `childKind`; no folder, `roomGen` or anything else), and of its sessions only those of a chat shown. A `createChat` sent to it carries only `chatId`, `spaceId` (its project) and `config`; a made chat's reply names the worker's device whatever it said. A worker made before project ids were its own (`work`) gets its own from its next start; its chats in the old `work` project no longer show (they stay in its volume). Worker rows are this device's own window's and CLI's only: a paired server dialling this one and the phone link see no worker and can't reach one. `zend worker run <name> "<prompt>" [--harness pi|mock] [--model <m>] [--timeout 600]` does the same from the command line: it makes the chat, runs the prompt and prints the reply, or past the timeout the chat's id and where to read it. `zend worker stop <name>` stops a running worker. Not yet: no limit on how many frames a second a worker sends (only their size, 16 MiB, and a list's rows, 5,000).

**Your subscription login per worker (step 4d-4 for workers).** A worker's Pi turns can run on the server's own pi login for one provider, if you allow it for that worker: `zend worker login allow <worker> <provider>` (`anthropic` or `openai-codex`), `zend worker login rm <worker> <provider>`, `zend worker login list` (`worker-logins.json`, mode 600, in Zend's data; this device's own methods, never over a peer link, the relay, a phone or from an agent). Before each run of a worker's chat leaves for it (`worker_turn` in `peer_view.rs`), the server picks the provider from the run's model (or the chat's): an API key the worker was made with wins; else, when allowed, it writes that provider's access-only entry (access token, expiry, Codex's account id, `refresh` empty, no other provider; refreshed first by the host's pi below 10 minutes, as for servers) to `workers/<name>/conf/login/<provider>.json` (file 644, folder 755, inside the worker's 700 folder; every folder checked to be this user's and not a link, the file written beside and renamed in, `O_NOFOLLOW`). `conf` is the server's alone and bound read-only into the container at `/etc/zend-worker` (since step 5), so the server writes by no path the worker can change, and a worker made before gets its login without being made again. Else the run is refused: the chat is told only "no credential for <provider> on this device", the reason goes to the server's log. No token is in the run or any frame to or from the worker. A login is lent for a turn, not for the allow: the server keeps each turn it lent for and removes the file once that turn's chat has settled (its session row not working for 5 s after it worked or finished a turn, or never working within 60 s), or its connection to the worker ends. One provider's login at a time per worker: a run on another provider while a turn on one is live is refused with the same text (the log says which chat holds the other), and a turn on a key or on nothing takes back every login no live turn holds. Each worker has a lock held across a turn's check of the allow, its refresh and its write, and by allow, `rm`, `zend worker stop` and `zend worker rm`, so an `rm` during a refresh waits for it and then removes what it wrote. The worker's engine copies what is lent for its pi (mode 444, one entry per lent provider, `refresh` empty) as each run arrives and within 2 s of any change, onto a tmpfs of its own at `/run/zend-login` (0700, made by the server at create, so never on the `/data` volume and never past the container's run); its pi's `auth.json` (`/data/pi`, its `PI_CODING_AGENT_DIR`) is a link to it, since pi needs a writable folder beside the file for its lock. The worker removes its copy and the link on SIGTERM and at start. A worker made before this tmpfs gets no copy (its log says why): make it again. `rm` of the allow removes the server's file at once and ends the worker's live turns on that provider (an interrupt to each over its socket; the CLI says how many). `zend worker stop` removes every file before and after the container stops, `zend worker start` before it starts, `zend worker rm` before it goes; the server clears all of them when it starts. The host's `auth.json` is never written by Zend nor mounted. The agent can read the access token while its turn runs; a token it copied stays valid until it expires (Codex tokens: days). Code: `crates/engine/src/worker_logins.rs` (`prepare_turn`, `settle`, `revoke`), `crates/engine/src/worker.rs` (`sync_logins`, `follow_logins`, `take_back_logins`), `crates/engine/src/workers.rs` (`interrupt`).

### The computer's plugins on a linked phone
A phone linked this way shows the plugins that are on at the computer: their sidebar items, pages and menus. The computer's engine has checked each one's signature and your decisions; it tells the phone no paths of its own, only which files each plugin is made of (relative path and sha256). The phone fetches them one by one (`ReadPluginFile`: only those files, from the plugin's checked copy, never through a link), checks each against the list, keeps them under `<app data>/plugins-remote/<id>/` and runs the window part from there. What a phone can't do (`commands`, `native`, `files`, `windows`, `web`) is left out as on any phone. A plugin's window calls its service on the computer, answered only for a plugin that's on and allowed there, with what it was allowed there; never another device's through the computer. It hears that service's events (`zend.service():on`) on a channel of the phone's own, only while the plugin is on and allowed there.
Code: `crates/engine/src/plugins/client.rs`, `apps/zgx/src/plugins/fetched.rs`.

### Ideas & Intents
A page under Search in the desktop sidebar for what comes to mind before it belongs anywhere. Type an idea and save it (⌘Enter): no title, project or chat. Or record a voice memo between Record and Stop, up to a minute, with the composer's dictation waveform under the buttons following what the microphone hears (from the recording's own samples): the recording is written to `<data>/ideas` as a WAV first, then transcribed on this device with the speech model Settings → Voice downloads. Without the model, or when transcription fails, the memo keeps its audio and says why, with Transcribe or Try again. Memos play from the page, also after a restart; newest first. Leaving the page (Settings, a chat, anywhere else) stops a recording and saves what was said until then; none records out of sight. A Save that fails keeps the typed words in the box. Nothing leaves the device and nothing goes to an agent. The composer's dictation is separate and still keeps no audio.
Code: `apps/zgx/src/ideas.rs`, `apps/zgx/ui/screens/ideas`. Plan: `plans/ideas-intents`.

### Edit a prompt, fork from a message
Hovering one of your prompts shows Edit: the prompt turns into an editor where it stands, its files and pictures kept as chips you can take off. Save & send asks once ("Removes N messages below. Files the agent changed are not reverted."), then the engine removes the prompt and everything below it for good and the edited words go as a new turn. The agent forgets the removed part: Zend drops the chat's provider session and the next turn starts a fresh one fed the kept history, on every harness. Not while a turn runs. Hovering any prompt or reply also shows Fork from here: a side chat with the conversation up to that reply, or up to just before that prompt with its words waiting in the side chat's message box.
How to use: [working-with-agents.md](working-with-agents.md), "Editing a prompt, forking from a message". Engine: `RewindChat`, `ForkSideChat` with `messageId`.

## For building plugins

All of these are described in [plugins.md](../apps/zgx/docs/plugins.md), section "The loop". Each has an MCP tool and a CLI command; the tools are listed in [mcp.md](mcp.md), "Plugin tools".

### Logs
The engine keeps what each plugin printed and what failed, with the full traceback: the last 500 lines in memory and in `logs/plugins/<id>.log`.
`plugin_logs { id, since? }` or `zend plugin logs <id> [--follow]`.

### Check
Syntax and types of a plugin's Luau before it runs, against Zend's window API, the plugin's `zend.luau` and the `@ds` modules. A file starting with `--!strict` is checked strictly. Types need luau-lsp; the first check fetches version 1.70.1 when none is found.
`check_plugin { id | path }` or `zend plugin check <id or folder>`.

### Pictures without a shown window
`plugin_status { id, snapshot = true }` returns a PNG of where the plugin shows, drawn for the picture, so the window need not be in front. With `page`, `width`, `height` and `state` it pictures one of the plugin's own pages without opening it.

### Preview apart from your window
A copy of a plugin's folder runs in a Zend of its own that never shows on screen, with a copy of what the plugin keeps and the permissions you allowed. `plugin_input` clicks and hovers there. It stops after 30 minutes without a call.
`preview_plugin { path }` or `zend plugin preview <folder>`.

### Preview in your window, Keep or Revert
A changed copy of one of your own plugins runs in your window in place of the kept version, with a bar offering Revert and Keep. Only the person can keep; an agent can start and revert.
`preview_plugin { path, in_window = true }` or `zend plugin preview <folder> --in-window`.

### `zend.run` in the plugin's folder
A program a plugin runs without a `cwd` starts in the plugin's own folder.
