# ADR 0007: A Stop names the sends it stops

- Status: Accepted
- Date: 2026-11-17

## Context

A Stop (an `interrupt` command) and the sends around it reach the chat's host by different roads: the doc's sync, the peer relay, in either order. The host had to tell two kinds of send apart. One kind was sent before the Stop: it is part of what the Stop stops, and must not run after it. The other kind is the person's next message: the Stop must leave it alone, and a late Stop aimed at a finished turn is moot. Every rule the host could compute on its own failed for some arrival order. Ledger order failed because a relayed command isn't in the ledger yet. Wall-clock send times failed on the same millisecond and on skewed clocks. A second review reproduced each failure in an engine run. The owner chose to fix it properly across devices.

## Decision

The Stop carries what it stops. `SessionCommandPayload::Interrupt` gets an optional `cancels`: the message ids of the sends its sender knew of whose rows weren't in its transcript yet (`zend_doc::sends_on_their_way`). Its `based_on.turn_id` (the sender's last row) already says which rows the sender knew. The engine (`queue_command_with_transfers`) and the window's client (`queue_command_as`) fill `cancels` in when they queue a Stop.

On the host:
- **Cancelling a send.** A send is cancelled if and only if a Stop claims it: the Stop names it, or its sender had its row (one up to the Stop's `based_on` turn) while it hadn't reached an agent yet. That holds even when the Stop itself is moot or gives way to a newer Stop: the person stopped that send either way. The host writes what it claims to its processed ledger on disk as it claims the Stop, before it acts: one key per name, and one for the turn it was aimed at, read by position (a row at or before that turn is claimed) and on its own (the turn itself is claimed with no row on this host), and also checks the Stops resolved in the doc's ledger. So the order the two arrive in doesn't matter, nor a restart in between. The claims also go to the sessions engine. There one function answers "may this message reach the agent" (`StopGate` in sessions.rs, reading disk and memory), and every road a message takes to an agent asks it as its very last step: under the run lock as its runtime is registered (a fresh send, a retry, a revival after a restart), again once its run is prepared and right before the harness starts (preparing is dropped when the Stop kills the run, so a stuck preparation holds up neither the Stop nor anything after it), and under the runtime's ledger lock as it is handed to a live one (a routed send, a steer, a queue row sent now, a steer redelivered after a turn stop). A claimed send therefore never runs after its Stop unless it reached the agent before the Stop's kill, and then the kill stops it.
- **When the Stop is moot.** It is moot only when a user row after its `based_on` turn is one it doesn't name, or when that turn is gone (a rewind removed it). Such a row is a message its sender didn't know of. No clock is compared.
- **What its sender saw.** The Stop carries its sender's doc version (2026-11-18): `based_on.frontier`, the Loro version vector of the sender's oplog as it built the Stop, hex-encoded (`zend_doc::encode_version`), read after the transcript its names and `based_on` turn come from. A transcript row is one its sender had if and only if the op that created the row (its map's container id) is in that version. That is the sender's knowledge whatever order the host's merge gives the rows: two devices' concurrent rows are ordered by peer id, so a turn started on the host after the Stop was built could land before the Stop's `based_on` turn, and judging by position took it for seen. Where this section and the two around it say "the rows up to its `based_on` turn", a Stop with a version means "the rows its version holds". The host finds a row's creating op through an index of the transcript's rows by message id (`SessionDoc::message_origin`), kept in step with the doc, so the check costs a lookup and no walk of the transcript. The version itself is kept where the Stop is: a Stop the host drained from the doc is read back from its entry there (resolved, or claimed in the processed ledger), after a restart too, and one that came by relay, not in the doc until it syncs, is kept in the processed ledger as a key that holds it (`stop-version:<chat>:<stop>:<version>`). The row the Stop was aimed at is still claimed on its own (`stop-aimed:<chat>:<message>`), for a host that doesn't have that row yet.
- **What the Stop kills.** The Stop waits for no send. It kills the live runtime (one registered for a turn that hasn't opened its stream counts too) only if every message that runtime was handed is one the Stop may stop: its names, the rows up to its `based_on` turn, and what continues them. The runtime keeps every message it was handed for its whole life; no count bounds it, so no count decides what a Stop kills. A runtime that was handed anything else is running a turn the sender never saw, and is left alone (the Stop resolves `superseded`). The decision and the retiring of the runtime happen in one step under the runtime's ledger lock, where sends are handed to it, so no turn reaches the runtime between them; a send after that step starts a fresh runtime, which the Stop doesn't touch. The queue's lock is tried only for a bounded time, so a wedged queue send can't hold the Stop up. (Attempts before this one made the Stop wait for its named sends and for prompts starting; each wait had a bound, and a dispatch slower than the bound broke the rule.)

A Stop that names its sends but carries no version (an engine from 2026-11-17) judges what its sender saw by position: the rows up to its `based_on` turn in the host's order, as before. A Stop without the field (an engine from before this change) keeps the old rules. It is moot when any row comes after its `based_on`, and it cancels the sends before it in the ledger.

Rejected:
- Ledger position. The ledger doesn't hold relayed commands yet.
- Comparing `issued_at` times. Clocks skew, and two commands can share a millisecond.
- A vector clock in `based_on.frontier`, at first: the sender's last row plus the sends it named looked enough. GPT's seventh review showed it isn't (the merge orders concurrent rows by peer id, not by what the sender saw), and the version went in (2026-11-18). The field was already on the wire, unused, so no wire or schema change was needed.
- Keeping the version of a drained Stop in the processed ledger too. The doc holds the Stop's entry, which holds the version; a second copy would be one more thing to prune.

## Consequences

- The wire shape of an old Stop is unchanged: `{"kind":"interrupt"}`. Older engines ignore `cancels` and judge a new Stop by the old rules.
- A send from a third device that the Stop's sender hadn't seen is not stopped by it, even if it was sent a moment earlier by wall time. That is the causal answer: the person couldn't have meant it.
- Sessions keeps the claims in memory too, per chat, for the engine's life; neither set is pruned yet (a follow-up).
- For a Stop with a version, a row the host doesn't have yet is claimed only by name or as the row the Stop was aimed at: until it lands, its creating op isn't known here. Once it lands, the version decides. For a Stop without one, "the rows up to the `based_on` turn" is read in the host's doc order, with the flaw above.
- The check a send makes as its last step costs a lookup once the row index is caught up (about 30 µs in a debug build at 10,000 rows), and the catch-up after the doc changed reads only rows it hasn't seen plus a pass over the list's containers (about 4 ms at 10,000 rows, debug). The walk it replaces cost 52-101 ms there. With no Stop in the chat, nothing is read (22 µs). A Stop without a version still walks.
- The host keeps every name a Stop gave, one processed-ledger key per name (`stop-cancel:<chat>:<message>`), and one per turn a Stop was aimed at (`stop-seen:<chat>:<message>`), across restarts. (Before 2026-11-17's second review it kept 256 per chat in memory, and lost them on a restart, when the Stop came by relay and its row hadn't synced.)
